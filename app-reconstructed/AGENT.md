## 0.0.47 独立交互决策、原生提问工具与档案词绑定

### 为什么这次修改执行机制

此前生产流式请求未注册提问工具，SSE 也没有接收 `tool_calls`。主动提问依靠模型在普通
正文里记得返回 `ask_user` JSON；同一步还要处理画图规则、正反提示词和中文释义，模型
容易把重要选择当成可以自行猜测的细节。现在聊天和绘图共用独立的交互循环：

1. **先决策**：单独核对原任务、已确认答案、档案与候选，不在此步编写提示词或中文释义，
   也不加载整段画图格式规则。向模型提供 `ask_user_question` 和 `continue_task` 两个动作，
   支持的接口使用 `tool_choice=required`。由模型选择“询问并等待”或“已有依据，可以继续”。
2. **有问题就暂停**：`ask_user_question` 直接生成 1–4 题的原生表单，保留真实选项、
   说明和稳定 ID；立即结束当前请求。等待期间不改工作流、不上传参考图、不提交出图，
   不保持网络请求，也没有倒计时默认选择。
3. **确认后续接**：Room 保存模型原始工具调用 ID、名称与参数。用户整批回答后，使用
   对应的 `assistant.tool_calls` 和 `role=tool / tool_call_id` 回传选中 ID、标签或自填内容；
   原任务、已确认答案和附件继续作为必需上下文。自然语言回答标明仍需模型检查是否答全。
4. **再编写结果**：`continue_task` 的决定以工具结果交给后续生成步骤；仍保留
   `ask_user_question`，新发现的重要冲突可继续问。明确交给 AI 的背景、动作等不机械询问。

这是模型决策后的工具派发，不是恢复按角色名、服装数量、普通回复关键词生成问题。
不会把推理文本中的“要确认”当作提问，也不会从 reasoning-only 输出恢复旧图去提交。
原有 JSON `ask_user` 交互仍可读取；不会重写用户已保存的人设、分镜或角色资料。

### 协议与接口兼容

- SSE 按 `index` 累积工具 ID、名称和 JSON 参数分片，处理 `finish_reason=tool_calls`，
  不要求一定还有普通 content 或 `[DONE]`。截断、长度终止、不完整参数和重复调用 ID
  不作为可执行动作。
- 每步只接受一个行动。无效工具、重复问题 ID、多个并行动作等最多反馈一次结构错误给
  模型修正，持续错误就结束，不无限重试、不偷偷采用第一项。
- 服务明确拒绝强制 `tool_choice` 时，保留原生工具并使用服务默认的自动选择；明确拒绝
  工具参数时才使用同样的独立 JSON 决策。兼容证据仅按 endpoint/model 保存在内存中，
  不靠模型名字猜支持性。超时、认证、额度、输出截断或其它参数错误不因此重发或降思考档位。
- 保留已有 `reasoning_content` 以续接工具调用，不将其冒充最终答复。工具定义、调用参数、
  回答与附图参与上下文预算；不为凑预算截断用户任务或必需答案。
- 正常继续完成通常是一次决策请求 + 一次正式生成；提问则只到提问步骤即结束。
  因而总请求次数可能较旧版增加；每次请求仍使用用户的思考档位和单次输出上限。
  停止可取消当前步骤，不会在停止后再启动下一次请求。

### 角色档案实际写入

- 原先“角色绘画词”只作为参考，只有另填的可选“固定词”和已选服装词自动补齐。
  现在未填写固定词的旧档案默认使用原有绘画字段，单角色漏词在写工作流前补齐，
  不再要求用户复制一遍到隐藏的固定词输入框；填写固定词时仍以用户明确指定的必须词为准。
- 比对完整词项，支持已有权重、下划线与空格，较长的猜测词不冒充真实触发词。
  角色名、别名和服装对话识别词仍不进入正反提示词，未启用或本轮排除的档案不激活。
- 用户明确修改外貌时，模型可在决策中返回
  `profile_overrides: [{character_id, tag, source_quote}]`；只接收当前已关联档案中的原词、
  以及能在原任务/已确认答案里找到的用户原句。已采用的覆盖随角色关联保存，
  下一轮改背景或清空反向不会悄悄恢复旧外貌；不采纳模型自己发明的引用或无关角色 ID。
- “清空反向提示词”等续改也保留上一画面的角色/服装关联；询问期间仍不补词出图。
  多人不将各人的标签机械拼成全局外貌，继续按角色资料由模型组织绑定句。
- 编辑页标明原字段的默认保留语义，以及填写可选固定词后其它外貌仅供参考的区别。

## 0.0.44 主动提问与回答续接（历史版本）

这次只扩展 Agent 交互，不推进工作区 P2–P4 页面，不调整底栏、页面动画或 Bridge。

### 使用方式

- AI 可根据任务自主提出问题，不再局限于角色、服装与词库冲突；用户要求“你能提问我吗”
  也可进入该动作。普通 Chat 和绘图模式都支持。
- 新问题支持一组单选、多选、自由填写题。选择题允许自行填写其它答案；点击选项只改草稿，
  所有题答完后点击“提交全部回答”一次发送，不逐选项请求模型。旧词库单题点选行为兼容保留。
- 显示“等待你回答”；没有挂起的网络请求，也不占用 busy。等待期间不加载/改写工作流，
  不上传参考图、不提交新任务。原来已经提交的服务器出图任务不自动取消，仍可独立运行。
- 回答后将原任务、先前已确认答案及本次答案作为必需上下文交给模型，再判断继续追问、
  普通答复、只写提示词或出图。继续追问时保留此前答案，不因历史裁剪丢掉原任务。
- 待答问题、结构化答案关联与原请求附件沿用 Room 消息及工作区资产保存；重开应用恢复等待状态，
  附图在用户确认后才提供给工作流。新附图优先于继承附图，继续遵守最多 4 张图的限制。
- 可直接在输入框自然语言回答，由模型判断是否还需补问；也可说“取消本次提问”，本地结束等待。
  明确的新任务（例如“画一只狗”或“新任务：……”）不续接旧问题、不继承其附图。
- 多题表单只接受当前问题的完整答案，拒收部分、过期、未知选项和重复发送。
  用户选中的标签与问题中未选角色名称分开，本地角色匹配不把未选名称当作绘画对象。

### 实现与兼容

- 应用输出契约增加 `action: ask_user / respond / apply_prompt / draw`。
  `ask_user` 带 `questions` 数组；每题 `id / prompt / kind`，选择项 `id / label`，
  用 `allow_multiple` 表示多选，填写题可有 `placeholder`。实际模型是否主动选择提问仍取决于模型输出。
- 提问优先于 `prompt` 和 `should_draw`；即使响应误带提示词、`true` 或截断的提问 JSON，
  也先等待，不沿用旧提示词出图。兼容 `ask_user_question` 动作名称和旧 `needs_clarification` 字段。
- 0.0.44 曾将“请先确认”“等你回答后再画”等普通文字转为填写题；
  0.0.45 已删除该启发式处理，仅接受模型显式的结构化提问。
- 修复绘图模式覆盖模型 `should_draw=false` 的旧决策；没有新提示词的普通问答也不再
  一律恢复上一张图。`respond` 不改工作流；有提示词的“只写提示词”仍写入而不提交。
- 用户自定义人设与分镜原文不覆盖。没有给兼容服务强行添加原生 `tools` 参数，
  也没有移植完整的第三方工具调用循环；当前采用 App 自身的结构化动作协议。

## 0.0.40 角色绘画词库消歧（历史版本）

  “本次不用角色库”均不注入；常驻不是让模型每次自行挑一个角色。

  恢复，不解析 AI 的回复来决定角色。重开应用后沿用已保存的记录；清空聊天即清除这份连续性。
  明确的新主体 / 新角色不沿用；最新画面没有角色关联时不越过它复活更旧的角色。

  另一套角色身份 / 译名候选，避免同名或机翻候选盖过用户登记的别名和自定义触发词。
  仅在查词用的副本中排除已关联名称 / 别名，避免大量同名身份和衍生词挤占场景词名额；
  发给模型的本轮原文保持不变。
  未使用用户角色档案时，离线角色查询仍照常保留。

## 0.0.30 上下文与单次输出长度

入口：**Agent 设置 → 模型 API 配置 → 上下文与输出长度**，编辑后点“保存并应用此配置”。
每套配置独立保存，聊天、提示词扩写、自动出图使用同一套本轮冻结设置。

- **上下文预算（tokens）**：可留空或输入 1024–2,000,000，提供 16K / 32K / 64K / 128K
  快捷选择。这是 App 的输入裁剪预算，不是向服务端声明或扩大模型真实上下文窗口。
  按 UTF-8 字节数加消息开销保守估算，图片每张预留 4096；不是具体模型 tokenizer。
  预算包含系统规则、本轮输入、参考资料、历史与输出预留，真实计数仍以服务端为准。
- **单次输出上限（tokens）**：可留空或输入 128–1,000,000，仅发送所选的
  `max_completion_tokens`（默认）或 `max_tokens`（旧兼容服务）。不同时发送两种字段，
  也不发送虚构的 `contextTokens` API 参数。新参数可能同时计入可见输出与思考 token。
- 上下文预算必须大于输出预留；没有指定输出上限时，App 为预算估算预留 4096，
  但请求仍不发送输出上限，实际跟随服务商默认。字段留空不是无限长度。
- 设置预算后最多选最近 200 条有效历史，从最早完整用户/助手轮次开始移除。
  系统规则、当前指令、词库候选和工作流参考保留整段；这些固定内容仍超预算时明确报错，
  不截断当前指令、不丢失正反向参考、不偷偷再发一次请求。
  未设预算时沿用聊天最近约 20 条、画图 4 条的历史数量限制。
- 输入非整数、超范围或输出预留不合适时显示具体提示，禁用保存；旧配置无需重新填写。
  每个请求使用发送时的配置副本，切换配置不让正在结束的旧请求覆盖新设置。
- 服务端不支持所选字段或上限时报告实际错误，不自动降级或重试。原有长度截断提示继续保留。
  App 填入更大的数字不会使服务商模型获得更大上下文或输出能力。

参数核对：OpenAI Chat Completions 官方参考（2026-10-18）：
https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create
未调用用户的付费模型；请求体、裁剪和出图链路使用本地 HTTP 夹具验证。

## 内核职责

- `agent/AgentSessionController.kt`：实例级 `AgentSessionState` / `AgentTurn`；
  发送前同步占用 busy、唯一请求身份、阶段与结束状态，避免连点重复发送。
- `agent/AgentConversationRunner.kt`：生成回复 → 应用提示词 → 可选提交三个步骤；
  `AgentDrawExecutor` 不负责调用 LLM，生成提示词本身也没有提交副作用。
- `ui/MainViewModelAgentRuntime.kt`：每个 ViewModel 的 Android 适配器，负责消息、
  附件、工作流加载、偏好设置和现有本地/RH 提交路径。
- `data/LlmClient.kt`：按 ID 管理实际 OkHttp Call；结束释放索引；协程取消绑定请求；
  连接/读取超时与 240 秒总时限分开报告；空流、格式异常、截断不再触发静默重发。
- `agent/AgentTool.kt`：typed `AgentTool` 接口及 `inspect_workflow`、`patch_workflow`。
  目前供内核调用，不要求模型支持原生 tool calling，也不把模型文字当任意命令执行。

`patch_workflow` 先整体校验再复制修改，返回字段 diff。修改能力来自提示词节点、
本轮图像节点和用户勾选的辅助参数；未知字段、连线、类型、范围和枚举错误使整批修改失败，
失败后不提交。`class_type`、节点拓扑和其他字段保持不变。

停止、清空聊天、切换服务器/模型配置/模板会使旧轮次失效；流式回调、最终结果与清理都按
turn ID 校验，旧任务不会覆盖新会话。独立的模板异步加载还有上下文代次和载入票据，
避免慢文件读取覆盖新模板。消息列表原子更新，进度刷新节流并在最终结果完整落盘。

**停止的边界**：停止本轮 LLM 和尚未提交的步骤；已被 ComfyUI / RunningHub 接收的任务
可能继续执行，本批没有新增远端任务取消工具。
